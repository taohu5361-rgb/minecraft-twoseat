Minecraft Java 单进程双人分屏模组

文档性质： 需求说明 + 技术架构草案 + 交给其他 AI 的开发交接稿。
版本： V1.0 ｜ 整理日期： 2026-11-12 ｜ 状态： 构想与可行性研究；尚未开发、未验证兼容性。
优先原则： 站在前人的肩膀上。优先使用现成开源模组及原版机制，最小修改，不重造轮子。

01｜项目一句话

在同一台 Windows 电脑、同一个 Minecraft Java 进程、同一份集成服务器世界中，支持两名真正独立的玩家；通过单屏左右分屏分别呈现两个摄像机，同时复用世界模拟、纹理、模型、区块网格和远景 LOD 缓存，尽量避免运行两套大型整合包客户端。

核心意图： 不是为了实现远程互联网联机，而是为了让本地两人合作游玩时，尽可能接近一次 Minecraft 游戏的资源开销。支持两人自由分开行动，不把副玩家限制为“自由摄像机”。

02｜设备与已有实测

条目 当前情况
CPU AMD Ryzen 7 9700X，8 核 16 线程
显卡 NVIDIA RTX 5070，12 GB 显存
内存 32 GB DDR5-6000
平台 Windows；Minecraft Java 版
整合包规模 当前整合包超过 400 个模组，含多种性能优化模组
后期游戏表现 单人后期常低于 60 FPS
GPU 利用率 不稳定，曾观察到约 50%，也常有 80%～90% 以上
CPU 总占用 常低于 50%；未提供逐核心/逐线程帧时间数据
分辨率实验 升高或降低分辨率，帧率常变化不大
视距实验 完整视距调至 8 区块时，帧率有时几乎翻倍，但远景体验明显变差

目前的性能判断： 完整区块视距是重要负载来源；分辨率不敏感可能意味着区块几何、渲染提交、CPU 主线程或其他非像素开销占主导。不能仅凭 GPU/CPU 总利用率认定瓶颈；具体情况仍需实测帧时间。

03｜必须实现的功能

  1. 真正双玩家： 两套独立玩家实体、坐标、生命值、背包、经验、交互、死亡及存档身份；彼此可以碰面、打怪、挖掘、建造。
  2. 单进程： 一个 JVM / Minecraft 客户端 + 一个集成服务器；避免把两个完整的 400 模组实例作为最终架构。
  3. 同屏双视角： 默认 1 块显示器、左右各半屏；两个摄像机独立转向与移动，各自有 HUD、物品栏和 GUI。
  4. 输入自由分配： 键鼠 + 手柄、双手柄、双键鼠均为目标组合；每个物理设备绑定到指定玩家，不串输入。
  5. 自由行动： 两人允许相距很远，各自加载近景；重叠区复用资源。不同维度是正式版目标，首轮单独验证。
  6. 远景不缩水： 每人近景完整渲染约 8 区块，远景由 Voxy 或同类 LOD 系统覆盖 64～128 区块（可配置）。
  7. 共享与稳定： 只模拟一份权威世界；共同区域不重复进行服务器模拟，存档可靠，优先兼容大型整合包。

暂不要求： 一开始就支持 3～4 人、开发新图形引擎、实现两套完整独立客户端、强制支持所有光影包，或承诺固定 FPS。

04｜目标架构

                 同一个 Minecraft Java 进程 / JVM
 ┌─────────────────────────────────────────────────────┐
 │                    输入设备分配层                   │
 │      键鼠 A / 键鼠 B / 手柄 A / 手柄 B（按需）      │
 ├──────────────────────┬──────────────────────────────┤
 │  玩家 A：实体/状态  │  玩家 B：实体/状态            │
 │  相机 A + HUD A     │  相机 B + HUD B               │
 │  8 区块完整近景     │  8 区块完整近景               │
 ├──────────────────────┴──────────────────────────────┤
 │  共享资源：纹理 / 模型 / 区块网格 / LOD 缓存        │
 │  对每个相机：分别做可见性判断和绘制                 │
 ├─────────────────────────────────────────────────────┤
 │      唯一集成服务器：区块 / 实体 / 红石 / Tick      │
 │              世界存档与两名玩家身份                 │
 └─────────────────────────────────────────────────────┘
                     ↓ 两个画面区域
          ┌────────────────┬────────────────┐
          │  玩家 A 半屏   │  玩家 B 半屏   │
          └────────────────┴────────────────┘

实现边界： 两个半屏合起来与原屏幕具有相同的输出像素数，但两套摄像机仍分别进行视锥裁剪、可见性判断、几何处理和部分特效计算。共享的是资源与可共享的计算结果，不能理解为“两个视角只需一次绘制”。

05｜区块、模拟与 LOD 策略

参数 初始目标 说明
完整渲染视距 每人 8 区块 可调 6～12；以目前实测的 8 为起点
LOD 远景视距 每人 64～128 区块 优先 Voxy；按版本兼容性考虑 Distant Horizons
服务器模拟距离 每人约 5～8 区块 建议初测 6；以服务器真实支持和玩法效果为准
缓存 同进程共用 LOD 数据源 允许不同相机复用 CPU 内存与 GPU 缓存；按需加载和淘汰
区块重叠 去重加载与模拟 世界区块以位置/维度标识；使用范围并集而非为每名玩家复制一份
区块分离 分别提出加载需求 玩家距离很远时，每人维护自己的近景范围

服务器侧： 同一世界的重叠区块原本就由服务器统一模拟；两人分开后，要模拟的是两人所需模拟区域的并集。模拟距离与渲染距离是不同设置，怪物 AI、机器、红石和农场在模拟范围外可能暂停。

客户端侧： 同一个区块网格、纹理、模型和 LOD 数据可以被两个视角引用；但每个相机都要根据位置和朝向分别筛选可见对象并绘制。远景预生成/预加载可减少实时计算和卡顿，并不意味着远景渲染成本为零；未探索区域需要先有可用地形数据。

理论规模说明： 若用正方形近似计算半径 r 的区块占用，(2r + 1)²：8 区块约 289 个，两人完全不重叠最多约 578 个；32 区块约 4,225 个。它只比较区块范围，不能直接推算 FPS、网格复杂度或内存用量。

06｜输入与分屏交互

  • 输入设备绑定逻辑独立于玩家与渲染：支持“键鼠 + 手柄 / 手柄 + 手柄 / 键鼠 + 键鼠”切换。
  • 双键鼠需要底层识别不同的物理鼠标/键盘，并解决窗口焦点、系统光标、快捷键以及 Raw Input 等平台问题；这是单独的兼容难点。
  • 每名玩家拥有自己的准星、HUD、物品栏、菜单焦点和操作权限。暂停游戏、聊天输入、打开设置、死亡画面等需要定义冲突处理。
  • 左右半屏可能影响横向视野、UI 排版及 FOV；应适配半屏宽高比，并允许 HUD 缩放。
  • 声音默认统一混音到电脑输出；若未来需要独立耳机输出，再作为后续功能。

08｜主要技术风险与应对

风险 为什么重要 优先应对
单本地玩家假设 Minecraft 与第三方模组往往默认只有一个 client.player、一个当前世界/摄像机 从现成单进程分屏项目入手，先验证真实双玩家交互
400+ 模组兼容 UI、实体渲染、机器、粒子、地图、背包等可能依赖全局客户端状态 先用精简包验证，再测试代表性大型整合包场景
Voxy / Sodium / 光影 渲染管线与缓存可能只为单摄像机设计 先无光影跑通两视角，再接 LOD，最后选测光影
远距离及跨维度 客户端世界状态、区块缓存、纹理与渲染生命周期不同 远距离作为核心验收，跨维度单列验证阶段
双键鼠 Windows 普通输入接口倾向将多鼠标合并 原生 Raw Input 或复用现有输入隔离模组
CPU 空闲但 FPS 低 总占用无法说明渲染主线程/服务器线程是否饱和 用帧时间和线程分析定位，不盲目“把 CPU 分成两半”
内存与显存 LOD 64～128、两视角近景仍可能造成缓存压力 缓存去重 + LRU/预算管理 + 显存监测
多人身份与存档 本地两名玩家须有独立 ID、数据和可靠恢复 设计会话创建/退出/重新进入时的身份映射

09｜最小开发路线（避免过度工程化）

  1. P0：一次性确定基础条件。 确认 Minecraft 版本、Fabric/Forge/NeoForge、Java 版本、整合包模组列表以及候选底座的修改许可。只做阻断性检查。
  2. P1：验证单进程双人最小闭环。 精简环境中，两人同屏、独立操作、独立物品栏、互相看见、正常挖方块和战斗；先不接入 LOD。
  3. P2：接入设备隔离。 先实现最容易成功的键鼠 + 手柄；再验证双手柄；双键鼠作为独立输入适配任务。
  4. P3：接入 8 区块近景 + LOD。 先单摄像机验证 Voxy/DH，再双摄像机验证缓存复用、远距离移动、切换/重建世界后的正确性。
  5. P4：性能与共享优化。 在真实整合包场景测试重叠区块和远距离区块；对确实重复的缓存、网格构建和加载进行最小修改。
  6. P5：大型整合包兼容与存档可靠性。 重点测试机器密集区、多人战斗、玩家死亡、传送、跨维度、退出再进入和长时间游戏。

执行纪律： 优先运行现成方案 → 发现可复现阻断问题 → 对必要位置打补丁 → 测试 → 交付。避免提前重构原版渲染引擎，也避免无休止的审计、预研和重复确认。

10｜验收与性能评估

功能验收： 两个真实玩家可相遇与分开；各自独立控制、HUD、背包和进度；方块与实体交互一致；重叠区块世界状态正确；远距离移动不卡死；存档可恢复。跨维度属于目标能力，应在兼容测试中单独验收。

性能基线（三组相同地点和环境）：

  1. 单玩家：8 区块完整视距 + 64/128 区块 LOD。
  2. 本方案：单进程两玩家、左右分屏、各自 8 区块 + LOD。
  3. 对照组（如能启动）：两个 Minecraft 实例本地联机、相近画质与渲染距离。

采集指标： 平均 FPS、1% low FPS、帧时间、GPU/CPU 帧耗时、GPU 利用率、显存用量、Java 堆与进程内存、GC 停顿、服务器 MSPT/TPS、区块加载数量。分别在两人靠近、相隔很远、机器密集区及探索新区块时记录。

成功标准： 双人可正常游玩且稳定；最终单进程方案在代表性场景中，相较双实例具有可观察的性能或内存优势。不提前承诺“接近单人 FPS”或固定倍数提升。

11｜待确认但不阻断方案讨论的事项

  • 目标整合包的 Minecraft 版本、模组加载器和 Java 版本。
  • 是否保留当前 400+ 模组整合包，还是换包；当前具体使用的优化模组与渲染链。
  • 屏幕分辨率、刷新率、是否需要光影；目标 FPS（如稳定 60）。
  • 实际输入设备型号，以及双键鼠是否为首版刚需。
  • 单进程分屏底座的源码、许可证与稳定性；现有 LOD 与双摄像机的兼容情况。
  • 两名玩家身份建立方法；本地会话是否允许额外朋友远程加入（当前不作为首版需求）。

12｜交给下一个 AI 的任务说明

请将此文档视为需求与技术方案草案，不要假定所有技术细节已经验证。优先帮助实现可运行原型，而不是重新从零开发 Minecraft 多人系统。

请按以下顺序输出： ① 检查最合适、源码许可允许修改的单进程分屏项目；② 找出其与目标 Minecraft 版本、加载器、Voxy/DH、Sodium 的真实兼容边界；③ 给出最小补丁清单，明确哪些可直接复用，哪些必须改；④ 先实现最小双人同屏样例，再逐步接 LOD 与输入隔离；⑤ 用 FPS/帧时间/内存/服务器 MSPT 测量改善。

约束： 优先复用现成轮子；保留两位玩家真实独立身份；远距离能自由探索；尽量保持兼容大型整合包；避免无依据的性能保证和不必要的框架重写。

版本备注： 本文档依据当前需求讨论整理。涉及第三方模组的支持范围、许可证和可修改性，均须以实际选定版本和最新项目资料为准。项目尚处于设计阶段。
